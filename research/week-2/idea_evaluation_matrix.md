# Week 2 — Idea Evaluation Matrix

| # | Idea | Component | Problem addressed | Mechanism | Evidence | Assumptions / limitations | Integration cost | Decision |
|---|---|---|---|---|---|---|---|---|
| 1 | Hybrid retrieval: BM25 + dense vector + RRF fusion | Retrieval augmentation | Pure vector search misses exact terms, IDs, version numbers, and anything where phrasing matters | Run both retrieval paths in parallel, fuse ranks (not scores) via Reciprocal Rank Fusion | Reported ~91% recall@10 in production write-ups vs. pure vector search failing on a reported ~40% of real queries; this is the converged production pattern across every 2026 source scanned, not a contested research question | RRF needs both a sparse and dense index maintained in sync; most modern vector DBs (Qdrant, Weaviate, Elasticsearch, Milvus) support both natively now, so this is less costly than it would've been two years ago | Low-medium — supported natively by most storage options already shortlisted in component 3 | **Adopt** |
| 2 | Cross-encoder / ColBERT reranking on top-k candidates | Retrieval augmentation | Fusion alone sometimes leaves the last bit of ranking quality on the table, especially for domain-specific corpora | Second-pass reranker rescores the top 20-50 candidates before they hit the context window | Consistently described as a real improvement, but every source qualified it as "add after benchmarking, not by default" | Adds latency and a second model call; easy to over-adopt as a reflexive fix rather than a measured one | Medium | **Defer** — implement fusion first, add this only if Deliverable 6 benchmarks show a real gap |
| 3 | No LLM call at retrieval time — push relevance judgment into index structure (BM25 + embedding + graph traversal) | Retrieval augmentation | LLM-judged relevance/recency at retrieval time is slow and expensive on every single turn | Structural retrieval (fusion + graph traversal) does the ranking; the LLM only sees the final result | This is Zep/Graphiti's production pattern, described as the most production-validated approach as of mid-2026 | Requires the earlier admission/ranking decisions (Week 1) to be good enough that structural retrieval doesn't need a model to compensate | Medium | **Adopt** |
| 4 | Explicit per-zone token budget (system prompt / retrieved memory / history / input / output reserve) with monitoring | Context construction | Context allocation is currently a zero-sum fight between memory, history, and tool output with no policy | Fixed token ceiling per zone, tracked and alerted on when a zone threatens to exceed its budget | Converged pattern across every 2026 context-engineering source this week; one concrete example budget cited for a 128K window | Zone sizes are workload-specific — this is a pattern to adopt, not exact numbers to copy | Low — mostly a policy/monitoring change, not new infrastructure | **Adopt** |
| 5 | Treat tool-output accumulation as its own budgeted zone, separate from history and retrieved memory | Context construction | A handful of tool calls can silently consume more budget than the visible conversation, and generic "history vs. memory" budgeting misses this entirely | Explicit budget ceiling and compaction policy for tool outputs specifically | Called out repeatedly as an underweighted failure mode in 2026 production write-ups on context overflow | Only relevant once this system starts being used inside agentic workflows rather than pure chat — may be premature for the MVP scope | Low | **Adopt** (design now, since retrofitting a missing budget zone later is more expensive than including it up front) |
| 6 | "Context rot" as a design constraint — don't rely on window size to solve the memory problem | Context construction | The instinct to just use a bigger context window and skip selective retrieval entirely | N/A — this is a constraint, not a mechanism | Measured performance degradation starting around 32K tokens even in million-token windows, reported across multiple 2026 sources | This is directional evidence from production write-ups, not a controlled benchmark I've run myself — worth treating as strong prior, not proven fact, until Deliverable 3 tests it directly | None — this changes reasoning, not code | **Adopt as a design principle**, validate empirically in Deliverable 3 |
| 7 | pgvector on existing Postgres for the MVP, migrate to a dedicated vector DB only past tens of millions of vectors | Index & storage layer | Avoiding premature infrastructure complexity | Single system, transactional consistency, standard SQL tooling, HNSW/IVFFlat support built in | Near-unanimous recommendation across every 2026 vector-DB comparison scanned this week for sub-tens-of-millions-vector workloads | Doesn't hold once true horizontal scale or hard per-tenant physical isolation is required — this is an MVP decision, not a permanent one | Very low — this is the "don't do extra work" option | **Adopt for MVP**, revisit at scale |
| 8 | Namespace-based tenant isolation now, physical per-tenant index isolation as an explicit upgrade path | Index & storage layer | Deliverable 1's tenant isolation constraint needs a concrete mechanism, not just a stated requirement | Namespace/metadata-scoped isolation is cheap and sufficient at moderate tenant counts; physical isolation is the harder guarantee for compliance-sensitive scale | Both patterns are well-documented production options (Pinecone-style namespaces vs. Weaviate-style physical isolation); no source suggested namespace isolation is unsafe at reasonable scale, just that it has limits | Namespace isolation is an application-layer guarantee, not a storage-layer one — a bug in query construction could leak across tenants in a way physical isolation would prevent structurally | Low now, meaningful cost if postponed and retrofitted later | **Adopt now, document the upgrade trigger** rather than deferring the decision |

## Summary

This week is more decisive than week 1, and that's deliberate — these three components have
genuinely converged production patterns behind them (unlike admission and lifecycle, which are
still being actively contested in the research). Where week 1 was mostly "adopt / prototype," this
week is mostly "adopt outright" with one explicit "defer" — reranking is a real technique, but
adding it before measuring whether fusion alone is sufficient would be solving a problem that
might not exist yet in this system.
