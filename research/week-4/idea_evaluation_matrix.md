# Week 4 — Idea Evaluation Matrix

| # | Idea | Component | Problem addressed | Mechanism | Evidence | Assumptions / limitations | Integration cost | Decision |
|---|---|---|---|---|---|---|---|---|
| 1 | Regex + NER as the PII detection pair, applied at both admission (pre-guardrail) and retrieval/injection (post-guardrail) | Privacy — PII handling | Deliverable 1's privacy constraint has no concrete detection mechanism yet | Two detector types catch complementary cases (structured data via regex, unstructured mentions via NER); applied at two separate pipeline points, not once | Converged pattern across every 2026 production guide scanned this week | PIIBench shows detector accuracy is unstable out-of-distribution (0.96 down to 0.18 in the worst case) — this is a real risk, not a hypothetical one | Medium — needs a chosen detector library and validation pass on this project's own data | **Adopt**, with mandatory validation on this project's conversational data before trusting any published benchmark number |
| 2 | Provenance tag on every memory record (user-stated / assistant-generated / tool-derived / retrieved-document) | Privacy & safety — trust laundering | The runtime currently has no way to distinguish trustworthy memory from memory that entered through a less-trusted channel | Every ADD/UPDATE operation from Week 1's admission framework carries an explicit provenance field, set at write time | Directly recommended by OWASP ASI06's mitigation triad (segment, expire, track provenance); "trust laundering" framing from multiple 2026 sources makes the risk concrete | Very low — Week 1's admission framework already has a natural place to attach this; this is additive, not a redesign | **Adopt** |
| 3 | Deterministic tenant filtering at query time, not similarity-threshold-based | Privacy — cross-tenant isolation | Namespace isolation (Week 2) is necessary but not sufficient — similarity search is probabilistic and can still produce cross-tenant collisions in hybrid/rerank pipelines | Hard filter on tenant ID applied before or independent of the similarity ranking step, not as a post-hoc score adjustment | Repeated point across OWASP ASI06 and the multi-tenant memory write-up scanned this week: "vector search is probabilistic, multi-tenancy requires determinism at the boundary" | This is a refinement of an existing Week 2 decision, not a new one — needs to be written explicitly into Deliverable 4 rather than assumed to follow automatically from namespacing | Low — this is a query-construction discipline, not new infrastructure | **Adopt**, explicitly amends the Week 2 namespace-isolation decision |
| 4 | Expire unverified memory rather than trusting it indefinitely | Privacy & safety — memory poisoning | An attacker-planted memory that goes unnoticed can persist and activate arbitrarily far in the future | Unverified or low-confidence memories (especially anything derived from tool output or external documents) get a default expiry unless corroborated or confirmed | Direct OWASP ASI06 mitigation recommendation | Interacts with Week 1's decay/lifecycle work — needs to be one more input to the existing four-lever consolidation framework, not a separate mechanism | Low — extends an already-adopted framework | **Adopt**, folds into Week 1's four-lever consolidation as an additional trigger for the decay lever |
| 5 | Deletion must propagate to derived/consolidated artifacts, not just the source record ("backflow" prevention) | Privacy — deletion guarantees | Week 1's adopted consolidation framework produces merged/summarized records; deleting a raw memory doesn't automatically un-summarize a derived artifact built from it | Track lineage from every derived artifact back to its source records; a deletion request cascades to every artifact derived from the deleted record, not just the record itself | "Backflow" and deletion-propagation framing from 2026 unlearning research and the Always-On Agents survey; directly connects to Deliverable 6's existing deletion acceptance check | This is a real, non-trivial engineering problem — lineage tracking adds a dependency graph that has to be maintained as consolidation runs | Medium-high | **Adopt as a requirement, prototype the lineage-tracking mechanism** before committing to a specific implementation |
| 6 | Treat PII detector accuracy as unverified until tested on this project's own data, regardless of published benchmarks | Privacy — PII handling | Published detector accuracy doesn't transfer reliably across text distributions | Build a small labeled validation set from this project's own conversational data (or realistic synthetic equivalent) and test any candidate detector against it before deployment | Directly motivated by the PIIBench OOD finding | Requires building a validation set specifically for this — extra work, but cheap relative to the cost of a false sense of security | Low-medium | **Adopt** |

## Summary

Five of six ideas are outright adopts — the mitigation patterns here are genuinely well-established
(OWASP ASI06's taxonomy in particular is doing a lot of the organizing work). The one idea flagged
as "adopt as a requirement, prototype the mechanism" (deletion propagation / backflow prevention)
is the hardest engineering problem this entire research phase has surfaced across all four weeks —
harder than supersession detection from Week 1, because it requires tracking derivation lineage
through an already-adopted consolidation pipeline, not just linking two records. This is worth
flagging honestly in Deliverable 4 rather than hand-waving a "we'll delete everything" claim that
the system can't actually back up.
