# Week 1 — Idea Evaluation Matrix

| # | Idea | Component | Problem addressed | Mechanism | Evidence | Assumptions / limitations | Integration cost | Decision |
|---|---|---|---|---|---|---|---|---|
| 1 | ADD / UPDATE / DELETE / NOOP as the admission action set | Memory admission | No clear basis for deciding what enters memory vs. gets ignored | Every extracted candidate is classified into one of four operations instead of a binary store/don't-store call | Used as the core action space in Memory-R1 and AgeMem, both RL-trained on it | Assumes the extraction step can reliably produce structured candidates in the first place; doesn't by itself solve *how* to score utility | Low-medium — this is a control-flow change, not a new subsystem | **Adopt** |
| 2 | Utility / confidence / novelty as separate admission factors | Memory admission | Single relevance score is too coarse to reason about or tune | Score each candidate memory on three independent axes rather than one blended score | A-MAC (2026) reports this decomposition improves interpretability of admission decisions over blended scoring | Needs three separate scoring functions instead of one — more moving parts to calibrate and evaluate | Medium | **Prototype** |
| 3 | Admit agent-generated commitments, not just user-stated facts | Memory admission | Assistant forgets its own prior decisions/recommendations even when user facts are captured correctly | Extraction runs over both user turns and assistant turns, treating assistant commitments as first-class memory candidates | Flagged as a known coverage gap in Mem0's 2026 field report | Risk of over-admitting — assistant chatter isn't automatically as durable as a stated user fact, needs its own filter | Low | **Adopt** |
| 4 | Deterministic `valid_until` supersession instead of LLM-judged recency | Ranking & conflict resolution | Similarity-based retrieval surfaces stale and current facts with equal confidence | When a new fact supersedes an old one, the old one is explicitly closed with a timestamp rather than just outranked | Graphiti/Zep's production model; directly motivated by the fact-consolidation benchmark results showing LLM-judged freshness performs poorly even with explicit instructions | Requires the system to detect supersession at write time, which is its own hard problem (two facts about the same "slot" need to be linked) | Medium-high | **Adopt** |
| 5 | Separate episodic and semantic memory into different indexes | Ranking & conflict resolution | Mixing dated events with general facts/preferences in one embedding space degrades retrieval for both | Two indexes (or two clearly tagged partitions) instead of one shared similarity index | Repeated warning across multiple 2026 sources (Nuanced Perspective write-up, agent memory surveys) | Adds a routing decision — every write and every query needs to know which index it belongs to | Medium | **Prototype** |
| 6 | Four-lever consolidation: importance / merge / decay / eviction | Reflection & lifecycle | "Cleanup" is currently one vague job with no clear sub-decisions | Treat each lever as an independent, separately-tunable decision instead of one consolidation pass | Framing from Hindsight's 2026 write-up on agent memory consolidation | This is an organizing framework more than a specific algorithm — still need to pick actual policies for each lever | Low (organizational, not a new component) | **Adopt** |
| 7 | Decay-as-reduced-accessibility, distinct from destructive deletion | Reflection & lifecycle | Conflating "this is getting less relevant" with "this must be gone" risks either over-deleting useful history or under-serving privacy deletion requests | Two separate mechanisms: rank-affecting decay (soft) and hard deletion (triggered by explicit request or safety policy) | Consistent point across the selective-forgetting taxonomy and the "Always-On Agents" survey | Requires the system to track two different states per memory instead of one | Low-medium | **Adopt** |

## Summary

Six of seven ideas are adopt-or-prototype this early, which is expected — week 1 is deliberately
scanning the components with the least-settled open questions, so most of what surfaces is
directly usable. The two flagged as **prototype** rather than **adopt** (utility/confidence/novelty
scoring, and the episodic/semantic index split) both need a small bounded experiment before they
go into the design, since each adds real implementation surface without a guarantee it beats a
simpler version.
