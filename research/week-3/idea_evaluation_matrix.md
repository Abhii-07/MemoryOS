# Week 3 — Idea Evaluation Matrix

| # | Idea | Component | Problem addressed | Mechanism | Evidence | Assumptions / limitations | Integration cost | Decision |
|---|---|---|---|---|---|---|---|---|
| 1 | Adopt recall / precision / latency (p50, p95) / token-efficiency as the core metric set | Evaluation | Deliverable 3 needs concrete metrics, not "qualitative observations" | Standard four-metric set converged across every benchmark and survey scanned this week | Used as the baseline metric set across LoCoMo, LongMemEval, and the 2026 survey's four-layer stack | Recall/precision alone don't capture whether a correctly retrieved memory was used correctly downstream — see idea 3 | Low — these are measurement definitions, not infrastructure | **Adopt** |
| 2 | Add a contradiction/staleness rate as a project-specific metric alongside the standard four | Evaluation | LoCoMo explicitly doesn't score knowledge updates, which is exactly this project's Week 1 focus (contradiction resolution) | Track how often a stale/superseded memory is retrieved ahead of, or alongside, its current replacement | Directly motivated by LoCoMo's acknowledged gap and this project's own Deliverable 1 Open Question 3 | Needs a labeled test set of superseded-preference conversations, which doesn't exist yet — has to be built specifically for this project | Medium | **Adopt** |
| 3 | Evaluate memory *use*, not just memory *recall* — task-level success, not retrieval accuracy in isolation | Evaluation | Recall accuracy in isolation can be a vanity metric — a system can retrieve the right fact and still fail to act on it correctly | Layer evaluation on top of retrieval metrics: does the final response/decision actually reflect the retrieved memory correctly | The MemoryArena finding — systems scoring near-perfectly on pure recall (LoCoMo) drop to 40-60% when memory has to inform an actual multi-step task — is the strongest single piece of evidence this week that recall-only evaluation is insufficient | This is meaningfully harder to build than a recall/precision harness — needs task scenarios, not just labeled Q&A pairs | Medium-high | **Adopt for Deliverable 6, defer full implementation** — Deliverable 3's baseline can start with recall/precision; task-level eval gets built once there's a real system to evaluate against |
| 4 | Be skeptical of LLM-as-judge for staleness/freshness specifically, keep it only for semantic-correctness scoring | Evaluation | Several benchmark papers use LLM judges broadly; Week 1 already found LLMs are unreliable at exactly the temporal-freshness judgment this project depends on most | Use LLM-as-judge for "is this answer semantically correct," never for "is this memory still current" — that gets decided deterministically per Week 1's adopted `valid_until` mechanism | Directly follows from Week 1's freshness-tracking finding — treating this as a closed methodological question rather than reopening the debate | None — this is a rule for how the eval harness is built, not new infrastructure | **Adopt** |
| 5 | OpenTelemetry GenAI conventions as the tracing substrate, with memory operations as their own span type | Observability | Deliverable 1 requires logs/traces for memory decisions with no specified mechanism | Instrument every memory operation (admission, ranking, supersession, decay, deletion) as a typed OTEL span nested under the parent agent run | De facto standard across every 2026 observability backend scanned (Braintrust, MLflow, OpenObserve, Uptrace); OTel GenAI working group is actively extending the spec to cover memory conventions directly | Requires committing to OTEL's span/event model rather than a custom logging format — a constraint, but a very low-risk one given near-universal tooling support | Low — auto-instrumentation exists for most common frameworks | **Adopt** |
| 6 | Memory content goes in span events, not span attributes, with collector-level redaction/hashing | Observability | Deliverable 1's privacy constraint requires sensitive content not leak into observability tooling by default | Events (filterable/droppable at the collector) instead of attributes (always indexed/exported); redaction happens at the collector level, not scattered through application code | Repeated pattern across every 2026 OTEL-for-LLM guide scanned; explicit redaction/hashing examples provided by multiple sources | Requires collector-level configuration discipline — a misconfigured collector could still leak content, so this is a strong default, not an absolute guarantee | Low | **Adopt** |
| 7 | Tail-based sampling: capture all errors, sample a fraction of routine traffic | Observability | Full tracing of every memory operation at scale is expensive and mostly redundant | Sample root spans at a low rate (e.g. 10%) for routine traffic; always capture spans associated with errors or flagged anomalies | Standard production pattern across multiple 2026 sources; explicit rationale given (LLM spans are large and slow, so 100% capture isn't free) | Sampling rate is workload-specific and needs tuning once real traffic volume exists — not a concern for the MVP stage | Low | **Adopt** |

## Summary

Evaluation and observability turn out to split the same way retrieval/context/storage did in Week
2 — mostly converged, adopt-heavy — with one important exception. Idea 3 (task-level evaluation,
not just recall) is the one genuinely hard problem in this batch, and it's the one I'd flag as the
most consequential finding of the week: a system that aces recall benchmarks can still fail
badly the moment memory has to inform a real decision, and Deliverable 3's baseline should be
honest about only measuring the easier half of that picture for now.
